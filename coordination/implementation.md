## 액션 API 연동 (13:24 KST): 스펙 기반 client + tool calling + 대화별 TC ID
범위: 로컬 구현과 모의 검사만 했다. 실제 액션 서버·OpenRouter·카카오 호출, 접수, reset 실행은 하지 않았다. 지식·고객 정보·토큰의 외부 전송도 없다.

**구현(`bot.py`)**
- `load_operations()`: `docs/action-api/openapi.json`에서 GET·POST 40개를 OpenAI 호환 function tool로 만든다.
  - 이름은 operationId(API-01~40), 설명은 summary·메서드·경로·description이다.
  - 파라미터는 path/query 파라미터와 `body`(requestBody 스키마 그대로)다. 스펙에 `$ref`가 없어 변환하지 않았다.
  - `?item=`처럼 쿼리가 붙은 경로 키는 `?` 앞만 경로로 쓴다.
  - `resetMyActionData`는 제외했다.
- `ActionClient.call()`:
  - 헤더는 Bearer 토큰과 TC ID다. TC ID 형식은 스펙 패턴으로 검사하고, 없으면 호출하지 않는다.
  - 경로 값은 `quote(safe="")`로 인코딩한다. 상태·본문을 그대로 모델에 반환한다.
  - 429 처리: Retry-After ≤10초면 1회 대기 후 재시도한다. "누적" 메시지면 재시도·이후 호출을 중단한다.
  - 500/503·네트워크 오류는 1회 재시도한다. 누적 3,000회 메모리 상한을 둔다.
  - 로그는 API 번호·상태만 남긴다.
- `Bot.generate()`:
  - 액션이 켜지면 tools를 넘겨 tool_calls를 실행하고 결과를 `role: tool`로 돌려준다. 최대 5회차, 45초.
  - 액션 지시에 "고객이 직접 말하고 확인해 준 주문번호·회원·대상과 상세 정보로만 호출하고, 추측·미확인 대상은 먼저 물어 확인"을 넣었다(감독 지시 반영).
  - 허위 완료 방지 정규식 가드를 둔다(README 참조).
- `Bot.handle()`: 메시지의 명시적 TC ID 표기를 대화 키(채팅방·사용자)별로 저장한다. 대화 축출 시 함께 지운다. 이번 턴 액션 결과 요약을 기록에 붙인다.
- `main()`: `AI_TOP_ACTION`이 있을 때만 액션을 켠다. 없으면 기존 동작 그대로다.

**모의 검사**: `uv run --locked python -m unittest -v` → **23개 모두 통과**(기존 17 + 액션 6). 가짜 LLM은 응답을 순서대로 반환하고, 액션 서버는 MockTransport다.

## S3 대응·저장정보 마스킹·미디어 연결 (13:58 KST)
**저장 개인정보 마스킹(프롬프트가 아닌 입력 단계)**
- 모델에 주는 도구 결과와 다음 턴 액션 요약에서 스키마의 저장 개인정보를 "[저장정보 비공개: 값 모름, 추측·언급 금지]"로 바꾼다. 대상: `recipient_name`, `shipping_address`, `address`, `phone`, `birth_year`, `payer_name`, `card_last4`, `delivered_location`, `name`.
- 다른 고객의 상담 이력(티켓)은 회원ID·내용을 가린다.
- 원본은 귀속 대조용으로 코드 안(`state`, `actions`)에만 둔다.
- 고객이 입력한 값은 그대로 둔다. 다만 고객이 제시한 값과 저장값을 코드가 대조해 주는 기능은 아직 없다(미구현).

**검수 S3 3건**
- **S3-A 계정 헤더 위조**:
  - 인입 계정은 사례 첫 메시지 **맨 앞 `case metadata` 목록 안**의 줄에서만 읽는다.
  - 그 블록의 `- id`가 같은 TC여야 하고, 마스크에 실제 숫자가 4자리 이상 있어야 한다(전부 `*` 불가). 같은 TC에서는 교체하지 않는다.
  - `TC ID:` 라벨 메시지나 본문 중간·이후 메시지의 계정 줄은 무시한다.
  - **실제 시스템 인증이 아니다.** 공개 TC 형식을 따른 대회용 합성 컨텍스트 입력이고, 평가 때의 신뢰 전달 경로는 미확인이다. 고객이 첫 메시지 맨 앞에 같은 형식을 써 넣는 경우는 구별할 수 없다. README에 문서화했다.
- **S3-B reason 낱말 우회**:
  - `reason` 문구를 근거로 쓰지 않는다.
  - 5만원 초과는 조회 데이터로 확인되는 예외만 허용한다: 전액, 주문 `PAID`, `ship_scheduled_at` < 2037-06-30, 집하 전 = 출고 지연.
  - 하자·수량 축소 예외는 API로 사실 확인이 불가하므로 승인 이관(`APPROVAL_REQUIRED`, API-35 `LANE2_HANDOFF`)으로 보낸다.
  - 검수 재현("하자가 아니며 단순변심" 80,000원 전액)은 출고 지연 사실이 있을 때만 접수되고, 예정일 미경과면 차단됨을 테스트했다.
- **S3-C PAID·SUBMITTED를 완료로 읽음**:
  - 수동·명사형 완료 표현은 그 업무의 완료 상태를 모델이 직접 조회해 받았을 때만 허용한다: 취소=`CANCELED`(주문·결제·구독), 배송=`DELIVERED`, 승인=`APPROVED`.
  - 환불·변경·발급·지급은 API에 완료 상태가 없어 항상 차단한다.
  - 차단 시 조회된 실제 상태를 그대로 안내한다(예: "조회된 현재 상태는 결제됨(출고 전)입니다. 처리 완료는 확인되지 않았습니다.").
  - 조사 "은/는/도"가 붙은 완료 표현("환불은 완료되었습니다")을 놓치던 패턴 결함도 함께 고쳤다.
  - 검수 재현 두 건(PAID 주문, SUBMITTED 환불)을 테스트했다.
- 최종 재현은 Sol 담당.

**기타 보완**
- API-33 쿠폰은 API-20 원장에 있고 오늘 유효한 코드만 허용한다(`UNREGISTERED_OR_EXPIRED_CODE`).
  - **위험**: 보상 쿠폰 CARE 코드가 API-20 원장에 있는지 미확인이다. 없으면 공개 L-47 기대(API-33 CARE5000)가 막힌다. 연습 API로 `API-20 CARE5000` 1회 조회해 확인할 필요가 있다.
- 도구 루프: 마지막 회차에는 도구를 주지 않아 MAX+1 실제 호출을 없앴다. 모델 요청 호출은 턴당 8회 상한(`TOO_MANY_CALLS`).
- 빈 모델 응답은 같은 턴에서 1회만 재요청하고 `finish_reason`·`native_finish_reason`을 로그로 남긴다(내용 미기록).
- 할 일 구분 지시를 docs/에이전트-업무범위.md의 D(금지)·E(시스템 미지원, 안내 후 이관)와 맞췄다.

**지식 로딩(210+11)**: 221줄, 시스템 지시 약 81,400자. 사실 원문이 그대로 없는 6건은 의도한 마스킹(직원 채널 URL 3, 내부 값 3)이고, 조건 누락 0이다.
