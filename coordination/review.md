### R1. 일반 단절 뒤 재접속에서 세션 복원을 포기함

- **동작·문제:** `resumed`는 이번 접속에서 복원 성공 여부가 아니라 접속 전 세션 존재 여부다. 따라서 세션을 가진 접속이 끊기면, 세션 만료 신호가 없어도 `or resumed` 때문에 세션·수신 순번이 초기화된다.
- **근거:** 연결 종료 프레임 없이 끊기는 `ConnectionClosedError(None, None)`를 두 번 모의했다. 접속 전 상태가 `(None, 0) → ('live-session', 42) → (None, 0)`으로 변했다. 세 번째는 RESUME에 필요한 상태를 잃는다. 기존 테스트는 명시적 4009 만료만 검사한다(`test_bot.py:111-128`).
- **최소 수정 방향:** 세션 무효가 확인된 경우에만 상태를 버리고, 일반 네트워크 단절에는 복원 정보를 유지한다. 연속 단절 회귀 테스트 하나로 확인한다.
- **남겨두면:** 네트워크가 반복해서 끊길 때 복원 대신 새 식별을 하므로 단절 사이 메시지 재전달을 보장할 수 없다. 실제 게이트웨이의 재전달 동작은 이번에 호출하지 않았다.

### R2. 일시적인 WebSocket 연결 준비 실패를 재접속하지 않음

- **동작·문제:** `run()`은 `ConnectionClosed`, `OSError`, `TimeoutError`만 처리한다. 연결 준비 과정에서 서버가 HTTP 503을 반환하면 `websockets.exceptions.InvalidStatus`가 발생하며 이 처리 목록에 포함되지 않는다.
- **근거:** `bot.connect`를 모의하여 `InvalidStatus(Response(503, ...))`를 발생시켰다. 접속 시도 1회 뒤 예외가 `run()` 밖으로 전파됐다. 실행 진입점도 이 예외를 처리하지 않는다(`bot.py:195-203`).
- **최소 수정 방향:** 일시적인 업그레이드 실패를 기존 대기·재접속 경로에 포함한다. 인증·프로토콜 등 치명 오류까지 무조건 재시도하지는 않는다. 503 이후 복구하는 모의 테스트가 필요하다.
- **남겨두면:** 짧은 게이트웨이 장애가 봇의 영구 중단으로 바뀐다. README에도 프로세스 자동 복구가 아직 없다고 명시되어 있다(`README.md:39-41`).

### R3. 운영 지식이 아직 답변에 연결되어 있지 않음

- **동작·문제:** 현재 시스템 메시지는 짧은 일반 지침과 도구 미연결 안내뿐이다. 초기 JSON의 사실·출처 또는 `interviews/knowledge.json`을 읽는 코드가 없다.
- **근거:** `httpx.MockTransport`로 승인 절차 질문의 모델 요청 본문을 확인했다. 확보한 이민준·고길동·5만원 규칙이 시스템 메시지에 없었다. 원본 위임표와 지식 파일이 존재하는 것만으로는 답변에 반영되지 않는다.
- **최소 수정 방향:** 구현 브리핑대로 작은 로컬 지식을 출처·조건·불확실성과 함께 연결하고, 파일 부재·작성 중 JSON에도 서비스가 유지되는지 검사한다. 새 검색 서비스나 가상 액션 API는 필요하지 않다.
- **남겨두면:** 승인 단계·환불 예외·미래 혜택 금지 등을 모델이 근거 없이 답할 수 있다. **구현 담당이 이미 맡은 예정 작업이며, 초기 상태의 미충족 사항으로 기록한다.**

### R4. 대화 잠금이 풀려 있다는 이유만으로 대기 작업의 대화를 제거함

- **동작·문제:** `create_task()` 직후 아직 실행되지 않은 작업의 잠금은 풀려 있다. 1,000개 대화가 차면 이 대화를 유휴로 잘못 판단해 제거할 수 있다. 같은 고객의 다음 메시지는 새 잠금·새 이력으로 처리된다.
- **근거:** 이벤트 루프에 실행 기회를 주기 전 서로 다른 고객 1,001명의 메시지를 넣고 첫 고객의 후속 메시지를 넣었다. `generate`와 `reply`만 모의하고 실제 `Bot.handle`을 사용했으며, 첫 고객의 `generate` 2개가 동시에 실행됨을 확인했다. 총 실행 4개 제한 안에서도 재현된다.
- **최소 수정 방향:** 실행 전·대기 중 작업이 있는 대화도 사용 중으로 취급하여 축출하지 않는다. 현재 잠금의 `locked()` 여부만으로 유휴를 판단하지 않는다.
- **남겨두면:** 동일 대화의 답변 순서와 앞선 대화 맥락이 깨진다. 다른 고객에게 이력이 노출되는 현상은 이번 재현에서 발견하지 않았다.

### R5. 포화로 버린 메시지를 이미 처리한 메시지로 기록함

- **동작·문제:** `seen` 기록은 대화 수용 여부를 결정하기 전에 추가된다. 대화 1,000개의 잠금이 모두 잡혀 있으면 새 메시지는 작업도 답변도 없이 반환되지만 중복 기록은 남는다.
- **근거:** 잠긴 대화 1,000개를 준비하고 새 메시지를 넣었다. 작업은 0개인데 `seen`에 그 메시지가 있었다. 잠금 하나를 해제한 뒤 같은 이벤트를 다시 전달해도 중복 판정으로 처리하지 않았다.
- **최소 수정 방향:** 메시지 수락이 확정된 뒤 중복 기록을 남기고, 포화 시 처리 방침을 분명히 한다. 콜백 성공 여부가 불명확한 메시지의 무조건 재전송과는 구분해야 한다.
- **남겨두면:** 잠깐의 포화가 고객 문의의 조용한 유실로 이어진다.

### R6. 대기 작업 수에는 상한이 없음

- **동작·문제:** 세마포어는 실행 중인 모델/콜백만 4개로 제한한다. 같은 대화로 들어오는 모든 메시지는 작업을 만들며, 대화 1,000개·중복 기록 10,000개 상한과 무관하게 누적된다. 만료 검사는 잠금·슬롯을 얻은 다음에만 한다.
- **근거:** 같은 대화의 서로 다른 메시지 1,500개로 작업 1,500개와 대화 1개가 만들어짐을 확인했다. 대기 작업이 일정 수에 도달하면 거부하는 분기가 없다. 예를 들어 동일 대화의 요청이 매번 20초 가까이 걸리면 뒤쪽 요청은 260초 기준을 넘어서 안내 없이 버려질 수 있다.
- **최소 수정 방향:** 대기 작업에도 유한한 상한과 포화 처리 경로를 둔다. 별도 큐 서비스나 프레임워크를 추가할 필요는 없다.
- **남겨두면:** 유입이 처리 속도를 넘는 동안 메모리와 응답 대기가 증가하고, 뒤쪽 문의가 만료된다. 실제 부하에서의 발생 빈도·p95는 미측정이다.

### R7. 지식 요약만으로는 일부 처리 분기를 복원할 수 없음

  - 위임표 p4 제9조③: 사유·근거를 남기지 않은 재량 처리는 다음 상담의 선례가 될 수 없다. 초기 JSON `112-115` / 인터뷰 지식 `66-71`는 기록 의무만 남겼다.

- **최소 수정 방향:** 확인된 누락 조건·분기만 원문 출처와 함께 보완한다. 미확보 규정의 접수기한·산식·조건은 추측으로 채우지 않는다.
- **남겨두면:** 지식을 연결해도 무증빙 하자, 반복 보상, 과거 거래의 적용 기준에서 필요한 근거가 빠진다. **누락 자체는 확인했지만 모델이 실제 오답을 하는지는 유료 호출 없이 판정하지 않았다.**
