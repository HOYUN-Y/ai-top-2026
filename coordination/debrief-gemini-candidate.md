대회 디브리프

## 1. 나의 AI 에이전트 강점

제가 가장 중요하게 생각한 부분은 고객의 상황에 맞는 근거를 찾아 다음 행동으로 연결하는 것이었습니다. 단순히 규정을 많이 아는 것만으로는 산지직송과 같은 복잡한 문의를 해결하기 어려웠습니다. 같은 상품이라도 주문 당시의 안내, 출고 상태, 배송 과정에 따라 확인해야 할 내용이 달랐기 때문입니다.

예를 들어, 냉동 수산물이 녹아 도착한 상황을 가정해 보았습니다. 수집한 사례들을 보면, 공식 기록상의 기사나 차량 정보와 실제 운행이 다른 경우가 있었고, 운송 중 온도 이탈 기록이 주문과 제대로 연결되지 않는 문제도 발견했습니다. 인계 시 온도가 정상이었다는 사실만으로는 중간에 발생한 문제를 파악하기 어려웠습니다. 그래서 저는 주문 상태와 현장 기록을 함께 보고, 담당자의 기억은 확인된 기록과 구분하여 활용하도록 했습니다. 또한, 고객 구제와 내부 책임 확인을 구분해야 한다는 규정도 함께 정리했습니다.

과거 홍보물이나 라벨을 보고 보상을 요구하는 고객에게 현재 규정만 제시하는 것은 불충분하다고 판단했습니다. 개정 시점과 당시 안내, 품목별 기준을 대조하고, 적용 조건이 불분명할 경우 임의로 결론 내리지 않도록 했습니다.

처리 권한 역시 중요한 고려 사항이었습니다. 주문번호를 안다는 이유만으로 타인의 정보를 알려주거나, 환불 요청이 접수되었다는 이유로 환불이 완료되었다고 안내하면 잘못된 기대를 심어줄 수 있습니다. 저는 주문의 귀속, 요청 접수, 실제 처리 완료를 명확히 구분하기 위해 모델 지시와 코드 검사를 함께 활용했습니다.

## 2. 어떤 접근으로 정보를 획득했는가

초기에는 필요한 정보를 폭넓게 질문했지만, 관계자마다 아는 범위가 다르다는 것을 깨닫고 고객 상황을 구체적으로 제시하는 방식으로 접근을 바꿨습니다. 배송 중 발생한 사실은 현장 담당자에게, 규정과 예외 승인은 해당 권한을 가진 사람에게 질문했습니다. 대화 중에 다른 사람이나 문서가 언급되면 다음 질문의 단서로 삼았습니다.

저는 누가 누구를 소개했는지, 직접 겪은 일인지 전해 들은 이야기인지, 사실을 아는 사람과 결정하는 사람이 누구인지 지식 지도에 기록했습니다. 한 사람이 모른다고 답해도 그 정보가 없다고 단정하지 않았습니다. 건당 200자 이하의 질문과 관계자별 사용량을 관리하며, 이미 막힌 경로를 반복하는 대신 후속 확인에 질문을 집중했습니다.

현재까지 10명의 관계자 중 8명과 업무 대화를 진행했으며, 감독하에 진행한 문답은 총 68건입니다. 이는 1~7차 확정 기록 64건에 8차 4건을 더한 수치이며, 제가 직접 나눈 문답은 별도로 기록했습니다. 기존 검수 스냅샷은 원본 자료 26개, 구조화 지식 238건과 초기 지식 11건으로 구성되어 있었습니다. 이후 부분환불 임계표, 축제 전단, 조직 관계도 ZIP 파일 3개를 추가로 확보했지만, 아직 원문 대조와 지식 반영을 진행 중이라 기존 수치에는 합산하지 않았습니다. 지식 건수는 내부 정리 항목 수이며, 대회의 공식 발굴 점수는 아닙니다.

자료를 정리할 때는 단순히 답만 추리지 않고 출처, 적용 조건, 예외, 미확인 사항을 함께 보존했습니다. 문서와 개인의 기억이 다를 경우 그 차이를 기록했고, 고객에게 공개할 내용과 내부 판단에만 쓸 내용도 구분했습니다.

## 3. 어떻게 검증했는가

저는 원문 대조, 코드 모의 검사, 실모델 평가, 실제 카카오톡 왕복을 구분하여 확인했습니다. 구현과 검수 역할을 나누어, 구현이 의도한 결과뿐만 아니라 잘못된 요청이나 대화가 이어질 때 발생할 수 있는 문제점도 살폈습니다. 공개 테스트 15개는 필요한 행동을 확인하는 기준으로 활용했습니다.

예를 들어, 타인 주문 조회를 거절했더라도 그 정보가 다음 대화에 남아있을 수 있었고, 여러 주문 중 하나의 취소 상태가 다른 주문의 완료 근거로 혼용될 수 있었습니다. 이를 해결하기 위해 거절 결과만 대화에 남기고, 상태를 대상별로 연결하는 방식으로 수정했습니다. 호출 제한에 따른 대기 시간과 큰 조회 결과의 절단 문제도 함께 점검했습니다. S8 지정 코드의 모의 검사 51개가 통과했지만, 이 결과가 전체 정확도를 의미하지는 않습니다.

실모델에서는 조회부터 배송지 변경 모의 접수까지 이어진 실행을 확인했습니다. 다만, 이후 도구 호출 형식 오류가 발생했고, 복구 재시도를 추가한 뒤에도 S9에서 해소되지 않았습니다. 따라서 최신 버전의 업무 수행이 안정적이라고 단정하지 않았습니다.

실제 액션 서버에서는 연습 사례인 CARE5000 프로모션을 GET 방식으로 한 번 조회하여 HTTP 200 응답을 확인했습니다. 실제 접수나 환불은 진행하지 않았습니다. 카카오톡에서는 액션을 끈 상태로 일반 상품 문의 한 건에 응답했습니다. 응답은 1개의 말풍선, 79자였으며, 봇 수신부터 콜백 성공까지 2,185ms가 소요되었습니다. 단일 표본이므로 평균 성능이나 p95를 측정했다고 볼 수 없으며, 전체 사례의 정확도도 아직 확인하지 못했습니다.

## 4. 주요 설계·구현

카카오톡 메시지를 로컬 Python 게이트웨이로 받아, 운영 지식과 대화 맥락을 모델에 전달하고 답변을 돌려주는 구조로 만들었습니다. 모델은 OpenRouter를 통해 Gemini 2.5 Flash를 사용합니다. 현재 규모에서는 별도 벡터 검색 시스템보다 정리한 지식을 직접 제공하는 방식을 택했습니다. 인터뷰로 확인한 조건과 예외를 빠르게 반영할 수 있었고, 지식 파일이 일시적으로 손상되면 직전 정상본을 유지하도록 했습니다.

업무는 직접 안내·조회, 조건부 접수, 승인·이관, 금지, 시스템 미지원으로 구분했습니다. 공식 액션 API 40종의 명세를 연결하되, 도구가 있다는 이유만으로 실행하지 않도록 했습니다. 대상과 귀속, 금액, 배송 단계 등 확인 가능한 조건을 검사하고, 정보가 부족하면 먼저 질문하도록 구성했습니다. API가 지원하지 않는 일은 안내나 담당자 연결로 이어가고, 처리 완료를 약속하지 않도록 했습니다.

대화는 채팅방 및 사용자별로 분리하고, 평가 사례가 바뀌면 이전 맥락과 조회 근거를 초기화합니다. 저장된 주소나 연락처를 먼저 읽어주지 않도록 조회 결과도 제한했습니다. 다만, 대회 입력에 포함된 계정 정보를 사용하는 방식은 일반 서비스의 로그인 인증과 같지 않아, 평가에서 정보가 전달되는 방식은 추가 확인이 필요합니다.

답변은 가능한 한 짧은 한 말풍선으로 전달하되, 필요한 안전 안내와 후속 질문을 생략하지 않는 방향으로 조정했습니다. 사진·음성 입력, 재접속, 중복 메시지 처리, 동시 작업 제한과 시간 제한도 구현했습니다. 로컬 자동 재시작과 절전 방지 설정은 준비했지만, 상시 운영 검증을 마친 상태는 아닙니다.

## 5. 아쉬움·한계

아직 모든 관계자와 운영 지식을 확보하지 못했습니다. 남은 두 명의 연결 경로가 미확인 상태이며, 추가로 받은 부분환불 임계표 등도 검수와 반영이 끝나지 않았습니다. 모르는 내용을 그럴듯하게 채우기보다 확인한 범위와 빈칸을 남겼지만, 그만큼 바로 답할 수 있는 업무에는 한계가 있습니다.

지식과 도구를 제공해도 모델이 필요한 후속 질문을 빠뜨리거나 잘못된 형식으로 도구를 호출하는 문제는 여전히 남아있습니다. 특히 `MALFORMED_FUNCTION_CALL` 오류는 S9에서도 재시도로 복구하지 못했습니다. 사진과 음성을 인식하는 것과 이후의 안전 질문이나 환불 사유 확인을 정확히 수행하는 것도 별개의 문제여서 추가 검증이 필요합니다.

속도와 안정성 또한 일반 질문 한 건만으로는 평가할 수 없습니다. 실제 액션과 동시 요청을 포함한 검증이 남아있으며, 메모리에 저장된 대화와 중복 처리 기록은 프로세스가 재시작되면 초기화됩니다. 로컬 환경은 전원, 인터넷, 절전 상태의 영향도 받습니다. 심사 종료일인 2026년 11월 1일 24:00 KST까지 안정적으로 운영하려면 실제 상시 실행과 복구 확인이 필요합니다.
