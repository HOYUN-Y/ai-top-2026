## 1. 나의 AI 에이전트 강점

가장 중점을 둔 강점은 **여러 근거를 대조해 고객에게 필요한 다음 행동을 정하는 것**입니다. 산지직송 문의에서는 상품이 무엇인지 아는 것만큼, 언제 어떤 상태로 출고됐고 어떤 안내를 받았는지를 확인하는 일이 중요했습니다.

예를 들어 냉동 수산물이 녹아 도착했다는 문의는 배송 완료 상태나 인계 순간의 정상 온도만으로 판단할 수 없습니다. 수집한 사례에서는 공식 배송 기록의 기사·차량과 실제 운행이 달랐고, 운송 중 온도 이탈 기록이 주문에 연결되지 않았습니다. 인계 시점에는 온도가 정상으로 돌아와 있었지만 중간 운송 로그에는 이탈과 복귀가 남아 있었습니다. 이처럼 주문 조회 결과와 현장 기록을 함께 봐야 하는 상황을 중요하게 다뤘습니다. 담당자의 기억은 단서로 활용하되 기록과 구분하고, 내부 책임 확인 때문에 고객 구제가 지연되지 않도록 관련 규정도 함께 정리했습니다.

또한 고객이 과거 홍보물이나 라벨을 근거로 보상을 요구할 때는 **현재 규정뿐 아니라 적용 시점과 당시 안내를 확인**하도록 설계했습니다. 일반 규정과 품목별 기준이 다르거나 개정 전후의 문구가 충돌하면, 한쪽을 임의로 골라 답하지 않고 적용 조건과 예외를 대조해야 하기 때문입니다. 해결되지 않은 충돌은 미확인으로 남기고, 규정이 정한 고객 선택이나 담당자 확인으로 연결하도록 했습니다.

개인정보와 처리 권한의 경계도 중요한 설계 기준입니다. 주문번호를 안다고 다른 사람의 배송 상태를 알려 주거나, 접수 응답을 받았다는 이유로 환불이 끝났다고 말하면 고객에게 실제 피해를 줄 수 있습니다. 따라서 대상 주문의 귀속을 확인하고, **조회된 사실·요청 접수·실제 처리 완료를 구분**하도록 했습니다. 이 부분은 모델 지시뿐 아니라 코드 검사와 독립 모의 검증으로 보완했습니다.

## 2. 어떤 접근으로 정보를 획득했는가

처음에는 관계자와 필요한 자료를 넓게 찾으려 했지만, 각 관계자가 알고 있는 범위와 권한이 달라 질문을 업무 상황별로 좁혀야 했습니다. 이후에는 “수산물이 상해서 도착했다면 무엇을 확인하는가”, “축제에서 산 상품 문제는 어디로 넘기는가”처럼 **실제 고객 상황 하나를 중심으로 질문**했습니다. 배송 현장 사실은 배송 담당자에게, 규정과 예외 승인은 운영자·조합장에게 묻는 방식입니다.

대화에서 다른 담당자나 기록이 언급되면 그 연결을 다음 질문의 근거로 삼았습니다. 누가 누구를 소개했는지, 직접 아는 사실인지 전해 들은 이야기인지, 사실을 아는 사람과 결정을 내리는 사람이 같은지를 지식 지도에 기록했습니다. 한 사람이 모른다는 답을 했다고 해당 정보나 담당자가 없다고 결론 내리지 않았고, 이미 막힌 소개 경로와 같은 질문을 반복하지 않도록 관리했습니다. 질문은 건당 200자 이하로 작성하고, 관계자별 사용량을 기록해 후속 확인을 위한 여유를 남겼습니다.

확인 시점까지 관계자 **10명 중 8명**과 직접 업무 대화를 진행했고, 감독하에 진행한 질문·답변은 **68건**입니다. 이는 1~7차 확정 스냅샷 **64건**에 8차 **4건**을 더한 수치이며, 사용자가 직접 나눈 문답은 별도 기록했습니다. 원문 대화, 링크, ZIP·PDF·표·이미지 자료를 보존하고 출처를 연결했습니다. 기존 검수 스냅샷은 첨부 원본 **26개**, 봇이 활용할 구조화 지식 **238건과 초기 지식 11건**입니다. 이후 부분환불 임계표·축제 전단·조직 관계도 ZIP **3개**를 추가 확보했으나, 원문 검수와 지식 병합이 진행 중이므로 기존 집계에는 합산하지 않았습니다. 지식 건수는 내부 정리 항목 수이며 대회의 공식 지식 발굴 점수나 완전성을 뜻하지는 않습니다.

지식에는 답만 넣지 않고 **출처, 적용 조건, 예외와 미확인 사항**을 함께 넣었습니다. 또한 고객에게 공개할 수 있는 정보와 내부 판단에만 쓸 정보를 구분했습니다. 문서와 기억이 다른 경우에는 차이를 지우지 않고 보존해, 답변에서 근거 없는 확신으로 바뀌지 않도록 했습니다.

## 3. 어떻게 검증했는가

검증은 원문 대조, 코드 모의 검사, 실모델 평가, 실제 카카오톡 왕복으로 나눴습니다. 자료 정리 담당이 만든 후보를 원문과 대조하고, 구현 담당과 별도의 검수 담당이 오류 상황을 재현했습니다. 공개 테스트 15개는 필요한 행동을 확인하는 기준으로 활용했으며, 사례별 정답을 코드에 고정하지 않았습니다.

특히 “테스트가 통과했으니 안전하다”는 판단에 머무르지 않고, 다른 고객의 주문 조회를 거절한 뒤 그 정보가 다음 대화에 남는지, 여러 주문을 조회했을 때 한 주문의 취소 상태가 다른 주문의 완료 근거로 섞이는지를 확인했습니다. 발견한 문제는 각각 거절 결과만 대화에 남기는 방식과, 상태를 개별 대상에 연결하는 방식으로 수정했습니다. 호출 제한 응답의 대기 시간과 큰 조회 결과가 잘리는 상황도 검증했습니다.

확인한 결과와 그 범위는 다음과 같습니다.

| 검증 | 확인한 결과 | 이 결과로 주장하지 않는 것 |
|---|---|---|
| 독립 모의 검사 | S8 지정 코드에서 **51개 통과**. 지정된 개인정보 유입·대상 상태 혼합·재시도·결과 절단 문제의 해결 확인 | 전체 사례 정확도, 모든 오류의 부재 |
| 실모델 평가 | OpenRouter의 Gemini 2.5 Flash로 합성 대화를 평가. 조회부터 배송지 변경 **모의 접수**까지 진행한 실행을 확인했고, 후속 실행의 도구 호출 형식 오류도 발견 | 실제 주문 변경 성공, 안정적인 전 사례 업무 완결 |
| 실제 액션 서버 조회 | 공개 연습 사례에서 `CARE5000` 프로모션 **GET 1회, HTTP 200** 확인 | 쿠폰 발급·환불 등 실제 접수 성공 |
| 실제 카카오톡 왕복 | 일반 상품 문의 **1건**, 답변 **말풍선 1개·79자**. 봇 수신부터 콜백 성공까지 **2,185ms** | p95, 평균 말풍선 수·평균 글자 수, 액션을 포함한 응답 속도 |

카카오톡 왕복은 액션 API를 끈 테스트 모드에서 확인했습니다. 실모델 평가의 액션은 모의 서버를 사용했으며, 실제 접수나 환불을 완료했다고 주장하지 않습니다. 도구 호출 형식 오류는 복구 수정 후 S9에서도 재시도로 해소되지 않았습니다. 따라서 복구 성공을 검증한 상태가 아니며, 이전 성공 실행과 최신 버전의 안정성을 구분하고 있습니다.

## 4. 주요 설계·구현

고객이 익숙한 카카오톡에서 문의하면, 로컬 Python 프로그램이 게이트웨이로 메시지를 받아 운영 지식과 대화 맥락을 모델에 전달하고, 결과를 콜백으로 응답하는 구조입니다. 모델은 OpenRouter를 통해 Gemini 2.5 Flash를 사용합니다. 별도 벡터 데이터베이스를 도입하기보다 현재 규모의 검수된 지식을 직접 제공해, 수집한 조건과 예외를 빠르게 반영할 수 있도록 했습니다. 지식 파일은 변경 시 다시 읽고, 일시적인 파일 손상 때에는 직전 정상본을 유지합니다.

업무는 **직접 안내·조회, 조건 충족 시 접수, 운영자 승인·이관, 금지, 시스템 미지원**으로 나눴습니다. 공식 액션 API 40종의 명세를 연결하되, 도구가 있다는 이유만으로 모든 요청을 허용하지 않습니다. 대상과 귀속, 금액, 배송 단계 등 확인 가능한 조건을 검사하고, 지원하지 않거나 근거가 부족한 업무는 처리 완료를 약속하지 않도록 했습니다. 판단에 필요한 주문번호나 상세 정보가 없을 때에는 먼저 고객에게 확인하는 흐름을 사용합니다.

대화 상태는 채팅방·사용자별로 분리하고, 평가 사례 ID가 바뀌면 이전 사례의 대화와 조회 근거를 초기화합니다. 저장된 주소·연락처를 먼저 읽어 주지 않도록 모델에 전달하는 조회 결과도 제한합니다. 접수 성공 응답은 요청이 기록됐다는 의미로만 다루며, 완료 표현의 근거는 작업과 대상별 상태에 연결합니다. 다만 대회 사례 머리의 계정 정보를 사용하는 입력 방식은 일반 서비스의 실제 로그인 인증과 같지 않으므로, 평가 전달 방식의 확인이 남아 있습니다.

응답은 가능한 한 짧은 한 말풍선으로 전달하되, 안전 안내나 필수 후속 조치가 빠지지 않도록 조정했습니다. 사진·음성 입력도 모델이 읽을 수 있도록 연결했고, 읽을 수 없는 첨부를 본 것처럼 답하지 않게 오류 경로를 마련했습니다. 네트워크 재접속, 중복 메시지 처리, 동시 작업 제한과 시간 제한도 구현했습니다. 로컬 자동 재시작·절전 방지 설정은 준비했으며, 실제 지속 운영 검증과는 구분해 관리하고 있습니다.

## 5. 아쉬움·한계

먼저 모든 관계자와 모든 운영 지식을 확보하지는 못했습니다. 남은 2명의 연결 경로가 미확인이고, 새로 확보한 부분환불 임계표 등은 원문 검수와 지식 반영을 마치지 못했습니다. 일부 질문은 담당자 사이에서 다시 돌아오기도 했습니다. 이 경우 그럴듯한 기준을 만들어 채우기보다, 어디까지 확인했고 무엇을 모르는지를 남겼습니다. 그 결과 즉시 답할 수 있는 범위에는 한계가 있지만, 근거 없는 금액이나 약속을 고객에게 제시하는 일을 줄이려 했습니다.

실모델은 규정과 도구를 제공받아도 필요한 후속 질문을 생략하거나 잘못된 형식의 도구 호출을 생성할 수 있었습니다. Gemini의 `MALFORMED_FUNCTION_CALL`을 확인해 제한된 복구 재시도를 보완했지만, S9에서도 재시도 후 오류가 해소되지 않아 복구 효과를 확인하지 못했습니다. 사진·음성 인식이 된다는 사실과 안전 질문·환불 사유 확인까지 정확히 수행한다는 사실도 다르므로, 이 부분은 추가 평가가 필요합니다.

속도와 운영 안정성 역시 최종 확인이 남아 있습니다. 카카오톡 약 2.2초 응답은 일반 질문 한 건의 측정값이며 p95가 아닙니다. 실제 액션을 포함한 여러 상황과 동시 요청으로 성능을 확인해야 합니다. 현재 대화·중복 기록은 메모리 기반이라 프로세스 재시작 시 초기화되고, 로컬 운영은 전원·인터넷·절전 상태의 영향을 받습니다. 심사 종료 시점인 현실 시간 **2026-11-01 24:00 KST**까지 유지할 상시 실행과 복구 검증을 완료한 뒤, 그 결과에 맞춰 최종 제출 문구를 갱신할 예정입니다.
