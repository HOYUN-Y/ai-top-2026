# 초기 로컬 봇 구축 작업기록 — p2

## 기록 범위와 담당 목적

이 문서는 초기 로컬 봇 구축 담당 세션에서 직접 수행한 작업을 기록한다. 목적은 `/Users/lyuhoyun/Documents/GitHub/ai-top-2026`에서 실행하는 프로그램을 카카오톡 봇과 연결하고, OpenRouter 모델의 답변을 실제 채팅방으로 돌려보낼 수 있는 최소 기반을 만드는 것이었다.

사용자와 계획을 구체화한 결과, 첫 구현 범위는 **카카오톡 연결부터**, 모델 선택 기준은 **비용 우선**으로 정했다. 당시 사용자 답변에 따라 대회 문제·인터뷰·액션 API 명세는 아직 공개되지 않은 것으로 취급했다. 지식 검색과 실제 주문 조회·환불·담당자 이관은 초기 구현에서 제외했다.

아래의 구현·테스트 결과는 이 세션에서 직접 수행한 이력이다. 마지막 절의 최종 운영 상태는 작업기록 작성 요청에서 전달받은 사실로, 이 세션이 구현하거나 확인한 결과와 구분한다. 이전 대화나 계획에서 알고 있던 내용은 배경으로 사용했으며, 기록 작성 시점에 코드를 다시 구현하거나 검증한 것으로 서술하지 않는다.

## 직접 수행한 작업과 산출물

### 저장소와 인증 설정 준비

초기 확인 당시 저장소에는 `.git`과 `.gitattributes`만 있었고 실행 가능한 앱은 없었다. 이 세션에서 환경변수 예제, 비밀 파일 제외 설정과 준비 안내를 작성했다. 사용자가 지정한 `AI_TOP_ACTION`, `KAKAO_REST_API`, `OPENROUTER_API_KEY` 이름으로 예제와 설명을 맞췄다. 실제 비밀 값은 출력하거나 문서에 복사하지 않았고, 값의 존재 여부만 확인했다.

이후 로그인된 공식 카카오 문서를 읽어 **REST API 키와 별개의 봇 인증 토큰**이 필요하다는 점을 확인하고 `KAKAO_BOT_TOKEN` 항목을 추가했다. 앞선 세 항목 확인만으로 인증 준비가 끝났다고 볼 수 없다는 점을 사용자에게 바로 정정했다. 실제 `.env`의 키를 임의로 채우지는 않았다.

관련 산출물: [환경변수 예제](../../.env.example), [Git 제외 설정](../../.gitignore), [실행 안내](../../README.md).

### 연동 방식 조사와 구현

처음에는 로컬 HTTP 서버를 임시 HTTPS 터널로 노출하는 구성을 검토했다. 공개 조회에서는 카카오 봇 문서가 404로 나타났으나, 사용자가 로그인하면 열린다고 알려 주었다. 브라우저 자동화 연결을 사용할 수 없어 열린 Chrome의 문서 화면을 읽는 방식으로 공식 명세를 확인했다. 이 조사는 당시 작업이며, 본 기록 작성 시에는 브라우저를 조작하지 않았다.

공식 문서에서 로컬 프로그램이 카카오에 직접 WebSocket으로 연결할 수 있다는 점을 확인했다. 사용자에게 선택지를 다시 제시했고, 사용자는 공식 게이트웨이를 선택했다. 이에 공개 HTTP 엔드포인트나 Tunnel 없이 다음 흐름을 구현했다.

`카카오 게이트웨이 → 로컬 Python → OpenRouter → 카카오 메시지 콜백 API`

핵심 구현은 [bot.py](../../bot.py)에 작성했다.

- 게이트웨이의 HELLO·IDENTIFY·READY 인증 흐름, heartbeat와 ACK 확인.
- 세션·시퀀스를 이용한 RESUME, 세션 만료 시 새 인증, 반복 장애의 지수 백오프.
- 인증 실패·잘못된 페이로드·다른 연결로 대체된 오류에서 무한 재접속하지 않고 종료.
- MESSAGE_CREATE 처리, 콜백 토큰 없는 이벤트 제외, 채팅방 키·메시지 ID를 이용한 중복 차단.
- 사용자·채팅방별 최근 6회 대화 기억, 같은 대화의 순차 처리, 전체 최대 4개 병행 처리.
- OpenRouter 1회 호출로 답변 생성, 최대 출력 256토큰·전체 대기 20초 제한.
- simpleText 말풍선 하나를 카카오 콜백 API로 전송하고 발송 성공 수·실패 수 확인.
- AI 오류 시 짧은 안내, 콜백 성공 여부가 불명확할 때 자동 재전송 방지.
- 비밀 키·콜백 토큰·대화 본문 대신 연결 상태, 오류 종류, 내부 응답 지연·글자 수 기록.

초기 기본 모델은 `google/gemini-2.5-flash-lite`였다. 실제 대회 액션 도구가 연결되지 않은 단계에서 실행하지 않은 업무를 완료했다고 답하지 않도록 시스템 지시에도 명시했다.

실행 환경은 Python 3.12 이상과 uv로 정하고 비동기 HTTP·WebSocket을 위한 두 직접 의존성만 추가했다. [pyproject.toml](../../pyproject.toml), [uv.lock](../../uv.lock)을 작성했으며, 당시 잠긴 직접 의존성은 httpx 0.28.1과 websockets 16.1.1이었다. 이후 다른 세션에서 파일이 변경됐을 가능성이 있으므로, 여기의 설명은 초기 작성 이력을 뜻한다.

## 주요 판단 이유

**공식 게이트웨이 선택:** 로컬 연결 시험에 필요한 외부 주소 등록과 터널 운영을 없앨 수 있었다. 사용자가 선택한 변경이며, WebSocket 수신과 HTTP 콜백 응답을 분리하는 카카오 명세를 따랐다. 웹훅 URL이 등록돼 있으면 게이트웨이를 사용할 수 없다는 사전 조건도 안내했다.

**작은 Python 프로그램 선택:** 로컬에 Python과 uv가 있었고 공식 예제도 같은 계열이었다. 별도 에이전트 프레임워크나 SDK를 도입하지 않고 필요한 통신만 구현했다. Python 정수로 공식 예제의 큰 메시지 ID를 다룰 수 있다는 점도 중복 판정에 유리했다.

**저렴한 모델·짧은 단일 답변:** 첫 목표가 연결 확인이었고 사용자는 비용 우선을 선택했다. 심사 기준의 속도·말풍선 수·길이를 고려해 불필요한 인사와 진행 메시지를 생략했다. 이 선택이 최종 심사 모델이나 최적 정확도를 입증한 것은 아니다.

**콜백 무조건 재시도 금지:** 네트워크가 끊겼더라도 원격 발송은 성공했을 수 있어, 재전송으로 중복 말풍선이 생기는 것을 피했다. 대신 일부 전달 불확실성은 한계로 남겼다.

## 검증 방법과 당시 실제 결과

실제 외부 호출 없이 httpx 모의 전송과 가짜 WebSocket으로 [test_bot.py](../../test_bot.py)를 작성했다. 최초 6개 테스트 통과 후 세션 만료와 치명적 종료 코드 테스트를 추가했다.

마지막 실행 명령은 `uv run --locked python -m unittest -v`였고, **8개 테스트가 0.021초에 모두 통과**했다. 당시 실행 출력에서 확인한 항목은 다음과 같다.

1. 발송 실패 결과를 성공으로 취급하지 않고 자동 재시도하지 않음.
2. 중복 이벤트 차단, 연속 질문의 맥락 유지, 다른 사용자 대화 분리, 콜백 토큰 누락 제외.
3. 게이트웨이 4009에서 만료 세션 초기화 후 새 연결 시도.
4. 4001·4003·4004에서 치명적 오류로 종료.
5. 최초 인증과 RESUME 프레임 및 ACK 처리.
6. AI 시간 초과·빈 응답·HTTP 오류에서 단일 오류 안내 전송.
7. heartbeat ACK 누락 시 연결 종료.
8. 잘못된 HELLO에서 오류 종료.

의존성 설치는 최초 제한 환경에서 DNS 오류로 실패했다. 같은 설치를 권한이 허용된 환경에서 수행해 성공했고 잠금 파일을 생성했다. `.env`가 Git 제외 대상인 것도 초기 준비 중 확인했다.

실제 실행 명령 `uv run --locked --env-file .env bot.py`도 수행했다. 실행 로그의 시각은 **2026-10-31 10:38:19,646**이며, `KAKAO_BOT_TOKEN` 누락 안내 후 종료했다. 이 시각은 당시 로그 표기를 그대로 기록한 것으로 별도 시계 검증을 하지 않았다. 따라서 **이 세션은 실제 게이트웨이 READY, 유료 모델 응답, 카카오톡 말풍선 수신까지는 확인하지 못했다.** 테스트 통과는 당시 초기 코드에 대한 결과이며 현재 최종 코드의 재검증 결과가 아니다.

## 미완료·한계와 다음 참고 사항

초기 구현 종료 시 남은 작업은 봇 인증 토큰 입력, 실제 카카오톡 질문·후속 질문·다른 계정 시험, 실제 네트워크 단절 복구 시험이었다. 사용자에게 이 상태를 보고했고, 키가 없어 실제 연결을 확인하지 못했다는 점을 명시했다.

당시에는 대화·중복 기록이 메모리에만 있어 재시작하면 사라졌다. 프로세스 자동 시작·장애 복구, 영구 지식 저장·검색, 액션 API 실행은 제공하지 않았다. 내부 지연 로그는 이벤트 수신부터 콜백 성공까지이며 앱 표시 시간이나 심사 측 p95와 같지 않다. README에는 실행·오류 확인·유휴 절전 방지 방법과 이 제한을 기록했다.

다음에 초기 구현을 참고할 때는 봇 인증 토큰과 REST API 키를 혼동하지 말아야 한다. 운영 봇에 테스트용 게이트웨이를 동시에 연결하면 기존 연결을 대체할 수 있으므로 실제 운영 중인 별도 프로세스 유무를 확인해야 한다. 초기 폴더의 기본 모델과 실행 명령을 최종 운영 설정으로 간주해서는 안 된다.
