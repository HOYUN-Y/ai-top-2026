## 1. 나의 AI 에이전트 강점

제가 가장 중요하게 생각한 부분은 **고객의 상황에 맞는 근거를 찾아 다음 행동으로 연결하는 것**이었습니다. 규정을 많이 아는 것만으로는 산지직송의 문의를 해결하기 어려웠습니다. 같은 상품이라도 주문 당시의 안내, 출고 상태, 배송 과정에 따라 확인해야 할 내용이 달랐기 때문입니다.

냉동 수산물이 녹아 도착한 상황이 대표적입니다. 수집한 사례에서는 공식 기록의 기사·차량과 실제 운행이 달랐고, 운송 중 온도 이탈 기록이 주문에 연결되지 않았습니다. 인계 때의 온도가 정상이었다는 사실만으로는 중간에 있었던 문제를 알 수 없었습니다. 그래서 주문 상태와 현장 기록을 함께 보고, 담당자의 기억은 확인된 기록과 구분해 활용하도록 했습니다. 고객 구제를 내부 책임 확인과 구분해야 한다는 규정도 함께 정리했습니다.

과거 홍보물이나 라벨을 보고 보상을 요구하는 고객에게도 현재 규정만 제시해서는 부족하다고 봤습니다. 개정 시점과 당시 안내, 품목별 기준을 대조하고, 적용 조건이 불분명하면 임의로 결론 내리지 않도록 했습니다.

처리 권한도 중요하게 봤습니다. 주문번호를 안다는 이유만으로 타인의 정보를 알려 주거나, 환불 요청이 접수됐다는 이유로 환불이 끝났다고 안내하면 잘못된 기대를 만들 수 있습니다. **주문의 귀속, 요청 접수, 실제 처리 완료를 구분**하기 위해 모델 지시와 코드 검사를 함께 활용했습니다.

## 2. 어떤 접근으로 정보를 획득했는가

초기에는 필요한 정보를 폭넓게 질문했지만, 관계자마다 아는 범위가 달라 고객 상황을 구체적으로 제시하는 방식으로 바꿨습니다. 배송 중 발생한 사실은 현장 담당자에게, 규정과 예외 승인은 해당 권한을 가진 사람에게 질문했습니다. 대화 중 다른 사람이나 문서가 언급되면 다음 질문의 단서로 삼았습니다.

누가 누구를 소개했는지, 직접 겪은 일인지 전해 들은 이야기인지, 사실을 아는 사람과 결정하는 사람이 누구인지 지식 지도에 남겼습니다. 한 사람이 모른다고 답해도 그 정보가 없다고 결론 내리지 않았습니다. 건당 200자 이하의 질문과 관계자별 사용량을 관리하면서, 이미 막힌 경로를 반복하는 대신 후속 확인에 질문을 쓰려고 했습니다.

업무 대화를 확인한 관계자는 **10명 중 9명**이며, 감독하에 진행한 문답은 **72건**입니다. 제가 직접 나눈 문답은 별도로 기록했습니다. 부분환불 임계표·축제 전단·조직 관계도 ZIP 3개의 독립 검수와 병합까지 마쳐, 현재 집계는 **원본 29개, 구조화 지식 255건과 초기 지식 11건**입니다. 원본은 수집 URL 28개에 해당하는 자료와 초기 위임표 1개이며, 중복은 없었습니다. 마지막으로 연결한 홍보걸에게서는 추가 자료를 받지 않아 자료 수는 그대로입니다. 지식 건수는 내부 정리 항목 수이며 대회의 공식 발굴 점수는 아닙니다.

자료를 정리할 때는 답만 추리지 않고 출처와 적용 조건, 예외, 미확인 사항도 함께 보존했습니다. 문서와 개인의 기억이 다르면 차이를 남겼고, 고객에게 공개할 내용과 내부 판단에만 쓸 내용도 구분했습니다.

## 3. 어떻게 검증했는가

원문 대조, 코드 모의 검사, 실모델 평가, 실제 카카오톡 왕복을 구분해 확인했습니다. 구현과 검수 역할을 나눠, 의도한 결과뿐 아니라 잘못된 요청이나 대화가 이어질 때 발생할 수 있는 문제도 살폈습니다. 공개 테스트 15개는 필요한 행동을 확인하는 기준으로 활용했습니다.

예를 들어 타인 주문의 조회를 거절했더라도 그 정보가 다음 대화에 남을 수 있었고, 여러 주문 중 하나의 취소 상태가 다른 주문의 완료 근거로 섞일 수 있었습니다. 이를 거절 결과만 대화에 남기고 상태를 대상별로 연결하는 방식으로 수정했습니다. 호출 제한에 따른 대기와 큰 조회 결과의 절단도 함께 점검했습니다. **S10 지정 후보의 독립 모의 검사 52개가 통과**했고, 별도 전체 로컬 검사에서는 봇·미디어 52개와 자료 검색 3개를 합한 **55개가 통과**했습니다. 검사 범위가 다른 결과이며, 어느 쪽도 전체 사례 정확도를 뜻하지는 않습니다.

실모델에서 발생한 도구 호출 형식 오류는 재시도 안내만으로 해결되지 않았습니다. 같은 대화에서 도구 인자의 구조를 비교하자, 중첩 구조는 실패하고 평면 구조는 유효한 호출을 만들었습니다. 이후 평면 구조로 진행한 배송지 변경 3턴에서 정확한 주문과 전체 새 주소로 모의 접수 한 건이 이뤄졌고, 형식 오류·저장 주소 노출·허위 완료 표현은 없었습니다. 다만 비교 실험은 각 한 번, 3턴 검증도 한 번이므로 원인이나 일반적인 성공률을 확정하지 않았습니다. 접수번호와 담당 확인이 남았다는 안내의 누락, 상세주소를 먼저 명확히 묻지 못한 점도 남겨 뒀습니다.

실제 액션 서버에서는 연습 사례의 CARE5000 프로모션을 GET으로 한 번 조회해 HTTP 200을 확인했습니다. **실제 업무 POST는 0회이며, 실제 접수나 환불은 하지 않았습니다.** 카카오톡에서는 14:13에 액션을 끈 테스트 봇으로 일반 상품 문의 한 건에 응답했습니다. 말풍선은 1개, 79자였고, 봇 수신부터 콜백 성공까지 2,185ms가 걸렸습니다. 이후 상시 서비스에서 축제 매대의 불량 수박 환불에 관한 합성 질문을 직접 보내 답변을 받았고, 제공한 응답 본문과 14:46:39 콜백 성공 로그가 일치했습니다. 이 응답은 말풍선 1개, 234자, 3,015ms였습니다. 온라인 조회·처리 불가, 조합 사무소 연락처와 시간, 구매 후 7일 이내 접수, 영수증과 상품 또는 사진 안내는 근거와 맞았습니다. 다만 원문에 없는 방문 필수 조건을 덧붙였으므로 완전한 정답으로 판단하지 않았습니다. 두 결과는 서로 다른 질문의 단일 표본 각각 1건이며, 평균 성능이나 p95·전체 사례 정확도를 확인한 것은 아닙니다.

## 4. 주요 설계·구현

카카오톡 메시지를 로컬 Python 게이트웨이로 받아, 운영 지식과 대화 맥락을 모델에 전달하고 답변을 돌려주는 구조로 만들었습니다. 모델은 OpenRouter를 통해 Gemini 2.5 Flash를 사용합니다. 현재 규모에서는 별도 벡터 검색 시스템보다 정리한 지식을 직접 제공하는 방식을 택했습니다. 인터뷰로 확인한 조건과 예외를 빠르게 반영할 수 있었고, 지식 파일이 일시적으로 손상되면 직전 정상본을 유지하도록 했습니다.

업무는 직접 안내·조회, 조건부 접수, 승인·이관, 금지, 시스템 미지원으로 나눴습니다. 공식 액션 API 40종의 명세를 연결하되, 도구가 있다는 이유만으로 실행하지 않도록 했습니다. 대상과 귀속, 금액, 배송 단계 등 확인 가능한 조건을 검사하고, 정보가 부족하면 먼저 질문하도록 구성했습니다. 도구 호출 형식 오류를 줄이기 위해 모델에는 인자를 평면 구조로 전달하고, 실제 요청 전에는 원래 본문 구조로 복원해 검증하도록 바꿨습니다. API가 지원하지 않는 일은 안내나 담당자 연결로 이어가고 처리 완료를 약속하지 않도록 했습니다.

대화는 채팅방·사용자별로 분리하고 평가 사례가 바뀌면 이전 맥락과 조회 근거를 초기화합니다. 저장된 주소나 연락처를 먼저 읽어 주지 않도록 조회 결과도 제한했습니다. 다만 대회 입력에 포함된 계정 정보를 쓰는 방식은 일반 서비스의 로그인 인증과 같지 않아, 평가에서 정보가 전달되는 방식은 추가 확인이 필요합니다.

답변은 가능한 한 짧은 한 말풍선으로 전달하되, 필요한 안전 안내와 후속 질문을 생략하지 않는 방향으로 조정했습니다. 사진·음성 입력, 재접속, 중복 메시지 처리, 동시 작업 제한과 시간 제한도 구현했습니다. 전용 사용자 폴더에서 launchd로 상시 실행하며 액션 40종을 활성화했습니다. 14:38:25 게이트웨이 연결을 확인했고, 강제 종료 한 번 뒤 14:39:26 자동 재시작과 재연결도 확인했습니다. 이는 서비스의 실행·복구 검증이며, 앞서 설명한 실제 고객 메시지 왕복 검증과 구분했습니다.

## 5. 아쉬움·한계

관계자 한 명은 아직 인터뷰하지 못했고, 자료를 추가로 검수해 지식에 반영했더라도 모든 예외 상황을 확인한 것은 아닙니다. 모르는 내용을 그럴듯하게 채우기보다 확인한 범위와 빈칸을 남겼지만, 그만큼 바로 답할 수 있는 업무에는 한계가 있습니다. 별도 자료 검색 기능도 시험했으나 동의어 누락이 남아, 이번 운영에서는 검색 결과만 추리는 대신 전체 지식을 제공하는 방식을 유지했습니다.

지식과 도구를 제공해도 모델이 필요한 후속 질문을 빠뜨리거나 근거에 없는 조건을 덧붙일 수 있었습니다. 최종 축제 환불 안내에서는 사무소 방문을 필수로 표현했고, 이미 끝난 행사 기간의 접수 경로까지 함께 안내해 답변이 길어졌습니다. 도구 구조를 바꾼 뒤 한 차례 모의 접수는 성공했지만, 접수번호와 처리 확정 전이라는 안내가 빠졌고 상세주소 확인 질문도 충분히 명확하지 않았습니다. 이전의 `MALFORMED_FUNCTION_CALL`이 모든 상황에서 해결됐다고 볼 근거도 아직 부족합니다. 사진과 음성을 인식하는 것과 이후의 안전 질문이나 환불 사유 확인을 정확히 수행하는 것도 별개의 문제여서 추가 검증이 필요합니다.

속도와 안정성도 일반 안내 두 건과 재시작 한 번만으로 평가할 수 없습니다. 실제 액션과 동시 요청을 포함한 검증이 남아 있고, 메모리에 저장한 대화와 중복 처리 기록은 프로세스가 재시작되면 초기화됩니다. 로컬 운영에는 전원·인터넷 연결, 덮개가 열린 상태와 사용자 로그인 유지가 필요합니다. 자동 재시작을 확인했어도 심사 종료인 **2026-11-01 24:00 KST**까지의 무중단 운영을 보장하는 것은 아니므로 실행 상태를 계속 확인해야 합니다.
